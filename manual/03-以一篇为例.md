# 03 · 以一篇为例（2021 英语一 · 阅读 Text 1）

这份文档把样例从头拆到尾。看完你应该能照着做出一篇新的。

## 1. 这一篇的概况

| 项目 | 值 |
|---|---|
| 篇目 | 2021 全国硕士研究生招生考试 英语（一）阅读理解 Part A Text 1 |
| 主题 | 英国铁路票价再涨：涨价理由、罢工补偿与国有化威胁 |
| 正文 | 4 段，387 词 |
| 真题 | 第 21–25 题，答案 D / B / C / D / D |
| 变体 | 6 道（词义句意、指代、例证作用、推理、否定事实、段落作用）|
| 逐词块 | 55 个（5 真题 + 6 变体，每题 5 块）|
| 产物 | `2021/docs/英语一2021_阅读Text1.html`，约 208 KB |

## 2. 四个文件，各管一段

```
2021/
├── SOURCE.md                     16.9 KB   四篇阅读的正文与题目原文（权威底本）
├── data/
│   ├── text1.words.txt           12.1 KB   正文逐词 387 词 + 标点，4 段
│   ├── text1.quiz.txt            14.6 KB   题干与选项逐词，55 块
│   └── text1.lesson.json         60.4 KB   段意、语法点、题目、解析、变体、词汇、主旨
└── docs/
    └── 英语一2021_阅读Text1.html  208 KB    ← 产物，单文件、零外部资源
```

注意 `SOURCE.md` 里是**四篇**（整份阅读理解），而 `data/` 只有 text1 这一套——因为样例仓库只配了一篇的数据。`build.py` 是按 `data/*.words.txt` 逐个构建的，数据有几份就出几篇。

## 3. 渲染链路

`python build.py 2021 1` 进来之后，`build.py` 依次做这几件事：

```
parse_words(text1.words.txt)      → [ {n:1, tokens:[{kind,w,ipa,gl,side}, ...]}, {n:2,...}, ... ]
parse_quiz(text1.quiz.txt)        → { "stem:21": [...], "opt:21:A": [...], ... }   每块一组 token
json.load(text1.lesson.json)      → {meta, para_notes, questions, variants, glossary, summary}

对每个 @N 段：
    render_para(tokens)           → <div class="para">…逐词 span…</div>
    render_grammar(para_notes[N]) → 段意卡片 + 语法点卡片

对每道题：
    _qline(quiz["stem:21"])       → 题干逐词 + 「译」行
    render_question(q, quiz)      → 题干 + 选项 + 答案徽章 + 四块解析

最后：
    page(title, body)             → 完整 HTML（内联 CSS 与 JS）
    写 2021/docs/英语一2021_阅读Text1.html
```

`check()` 在中途会拦一道：音标是否 `/.../` 包裹、释义是否超长、段数与 `para_notes` 是否对得上、真题是否 5 题、变体是否 6 题、每题块数是否够。任何一条不过就打 `!` 告警，但**不会中止构建**——产物照样生成，你要自己看告警。

## 4. 解剖一：一句话怎么变成 HTML

拿第 1 段第一句：

> How can the train operators possibly justify yet another increase to rail passenger fares?

### 4.1 输入：`words.txt` 里是这样几行

```
@1
How|/haʊ/|adv. 怎么
can|/kæn/|modal. 能
the|/ðə/|art. 定冠词
train|/treɪn/|n. 火车
operators|/ˈɒpəreɪtəz/|n. 运营商
possibly|/ˈpɒsəbli/|adv. 究竟（加强语气）
justify|/ˈdʒʌstɪfaɪ/|v. 为…辩解
yet|/jet/|adv. 又（再一次）
another|/əˈnʌðə/|adj. 又一次的
increase|/ˈɪŋkriːs/|n. 上涨
to|/tu/|prep. 在…上
rail|/reɪl/|n. 铁路
passenger|/ˈpæsɪndʒə/|n. 乘客
fares|/feəz/|n. 票价
?|_|_
```

最后一行那个 `?` 就是「标点也占一个 token」。

### 4.2 中间态：先合并标点

`render_para` 不直接吐 HTML，先把 token 整理成一个 items 列表，按标点的「贴哪边」分三类处理：

| 标点类型 | 例子 | 处理 |
|---|---|---|
| 后置（`side=="L"`） | `,` `.` `?` `:` `;` | 追加到**前一个词**的尾部 → `fares?` |
| 前置（`side=="R"`） | `(` `"` `“` | 并入**后一个词**的开头 → `(CPI)` |
| 两侧型 | `—` `–` | 单独站成一个 `.wd.wd-pc` |

这一步是为了解决一个真实缺陷：早期实现把每个标点都渲染成独立的 span，结果 flex 换行时行首会出现孤零零一个冒号（`": or otherwise"`），非常难看。改成「标点跟着词走」之后，`ritual:`、`rises,`、`year's,`、`(CPI)` 全部紧贴，行首不会再出现孤立标点。

直引号 `"` 是个特例——它本身分不出开还是闭，所以按**出现顺序奇偶配对**：第 1、3、5…个当开引号贴后一个词，第 2、4、6…个当闭引号贴前一个词。这样 `that" the` 被修正成 `that` + `"the … service,"`。

### 4.3 输出：每个词长这样

```html
<div class="para">
  <span class="wd">
    <span class="an">
      <span class="ipa">/haʊ/</span>
      <span class="gl">adv. 怎么</span>
    </span>
    <span class="tx">How</span>
  </span>
  <span class="wd">
    <span class="an">
      <span class="ipa">/kæn/</span>
      <span class="gl">modal. 能</span>
    </span>
    <span class="tx">can</span>
  </span>
  ...
</div>
```

每个词是一个 `.wd` 容器，里面**上下两层**：

```
┌──────────────┐
│   /ˈɒpəreɪtəz/  │   ← .an 上层：音标（棕褐）+ 词义（青）
│   n. 运营商      │
│   operators     │   ← .tx 下层：英文词（黑色）
└──────────────┘
```

### 4.4 为什么这样写就不会重叠

这是整套排版最要紧的地方，说清楚：

```css
.para{
  display:flex;
  flex-wrap:wrap;      /* 一行放不下就换行 */
  align-items:flex-end;/* 各词底部对齐，注释高度不同也不歪 */
  row-gap:var(--rowgap); /* 行与行之间 30px */
}
.wd{
  display:inline-flex;
  flex-direction:column; /* 注释在上、词在下，纵向堆 */
  align-items:center;
}
.wd .an{ max-width:134px; text-align:center }  /* 长注释可折行，不撑宽词位 */
.wd .ipa{ white-space:nowrap }                /* 音标不折 */
```

关键在**没有任何绝对定位**：

- 注释 `.an` 和词 `.tx` 是 `.wd` 的**兄弟子元素**，在同一个纵向 flex 容器里。
- 所以 `.wd` 的高度 = 注释高度 + 词高度，浏览器自己算。
- 某一行里出现一个三条注释的长词，那一行自动变高，`row-gap` 保证下一行不会压上来。

对比一下常见的错误写法——把注释用 `position:absolute; top:-20px` 挂到词上方：

```css
.wd{ position:relative }
.an{ position:absolute; top:-20px }   /* ✗ 不要这样 */
```

这样注释脱离了文档流，既不占高度也不影响行高，一旦某行注释变高就直接压到上一行去——这就是字体重叠的根源。**本项目从结构上排除了这种可能**，不是靠调参调出来的。

另外两个细节：

- `.an` 给了 `max-width:134px`：释义太长时在注释内部折行，而不是把整个词位撑得很宽。
- `.ipa` 给 `nowrap`：音标不能被拆成两行，否则 `/ˈɒpəreɪtəz/` 会在中间断开。

代价是**词间距必然偏大**——每个词位的宽度由「词本身」「音标」「释义」三者中最宽的那个决定，短词旁边站着一个释义较长的词，就会有一段空白。这是「逐词上方标注」这个格式的固有成本，不是 bug。

### 4.5 段尾：段意与语法点

正文之后紧接着两张卡片：

```html
<div class="trans">
  <b>段意</b>
  <p>火车运营商究竟凭什么能为铁路客运票价的又一次上涨辩解？……</p>
</div>

<div class="gram">
  <div class="gram-h"><span class="gram-ico">语</span>本段语法点 · 必须掌握</div>
  <ul>
    <li>
      <b>① 修辞性反问：How can the train operators possibly justify …</b>
      结构：…<p class="gr">考点：…</p><p class="gr">例：…</p>
    </li>
  </ul>
</div>
```

`lesson.json` 里 `grammar[].b` 用 `\n` 或 `<br>` 分隔出的「结构 / 考点 / 例」三行，在这里被 `render_grammar` 拆成三个 `<p class="gr">`——每行独立成段，行距 2.0，所以不会挤成一坨。

## 5. 解剖二：一道题怎么变成 HTML

拿第 21 题。

### 5.1 输入：两个文件各出一半

`quiz.txt` 管**排版用的逐词数据**：

```
@stem:21
The|/ðə/|art. 定冠词
author|/ˈɔːθə/|n. 作者
holds|/həʊldz/|v. 认为
...
______|_|_
~ 作者认为，今年铁路客运票价的上涨 ______。

@opt:21:A
will|/wɪl/|modal. 将
ease|/iːz/|v. 减轻
train|/treɪn/|n. 火车
operators'|/ˈɒpəreɪtəz/|n. 运营商（所有格）
burden|/ˈbɜːdn/|n. 负担
~ 会减轻火车运营商的负担
```

`lesson.json` 管**题目语义与解析**：

```json
{
  "no": 21,
  "type": "细节题",
  "stem": "The author holds that this year's increase in rail passenger fares ______.",
  "options": {"A": "will ease train operators' burden", "B": "...", "C": "...", "D": "..."},
  "answer": "D",
  "locate": "第一段第③句（配合第②句）",
  "blocks": [
    {"k": "原句含义", "t": "..."},
    {"k": "语法辨析", "t": "..."},
    {"k": "难点解析", "t": "..."},
    {"k": "易错点解析", "t": "..."}
  ]
}
```

**两边必须对得上**：`src` 里的 `stem`/`options` 文本，与 `quiz.txt` 对应块拼起来的文字，去掉空白后必须完全一致。这是 `qc.py` 的活。

### 5.2 输出：题目卡的结构

```html
<article class="q">
  <div class="qhead">
    <span class="qno">第 21 题</span>
    <span class="qtype">细节题</span>
  </div>

  <!-- 题干：逐词 + 译行 -->
  <div class="para qz"> … 逐词 span … </div>
  <div class="qzcn"><b>译</b><div class="qzw"><p>作者认为，今年铁路客运票价的上涨 ______。</p></div></div>

  <!-- 选项：两列网格 -->
  <div class="opts">
    <div class="opt"><span class="k">A</span><div class="obody"><div class="para qz">…</div></div></div>
    <div class="opt"><span class="k">B</span><div class="obody"><div class="para qz">…</div></div></div>
    <div class="opt"><span class="k">C</span><div class="obody"><div class="para qz">…</div></div></div>
    <div class="opt ok"><span class="k">D</span><div class="obody"><div class="para qz">…</div></div></div>
  </div>

  <!-- 答案与定位 -->
  <div class="ansline"><span class="ans">答案 D</span> 定位：第一段第③句（配合第②句）</div>

  <!-- 四块解析 -->
  <div class="blk k1"><span class="tag">原句含义</span><p>…</p></div>
  <div class="blk k2"><span class="tag">语法辨析</span><p>…</p></div>
  <div class="blk k3"><span class="tag">难点解析</span><p>…</p></div>
  <div class="blk k4"><span class="tag">易错点解析</span><p>…</p></div>
</article>
```

几个要点：

- **选项用两列网格**：`.opts{display:grid;grid-template-columns:repeat(2,minmax(0,1fr))}`，A/B 在左列、C/D 在右列。窗口窄于 980px 时自动回退单列。这样一屏就能看完一道题加解析开头。
- **正确项带 `ok` 类**：绿底 + 字母后面加 ✓。
- **字号分三档**：题干 `--tx:15px`、选项 `--tx:13.5px`、正文 `--tx:17.5px`。题干比选项大、比正文小，视觉层次才不乱。

### 5.3 四块解析的样式映射

`lesson.json` 里 `blocks[].k` 只能是这四个字符串，顺序固定：

| 顺序 | `k` 值 | CSS 类 | 配色 |
|---|---|---|---|
| 1 | `原句含义` | `k1` | 米黄 |
| 2 | `语法辨析` | `k2` | 淡蓝 |
| 3 | `难点解析` | `k3` | 淡紫 |
| 4 | `易错点解析` | `k4` | 淡粉 |

写成别的（比如「难题解析」）那个块就匹配不到类名，退化成无色块——`_allcheck.py` 专门查这个，因为这类错字肉眼很难发现。

四块各自要写什么：

- **原句含义**：先给定位句原文（`**粗体**`），再给中文译文，再点出这句与正确选项的对应关系。
- **语法辨析**：把这句话拆开讲，①②③④ 分条，讲骨架、时态、搭配、修饰关系。
- **难点解析**：说清「这题到底难在哪」——是态度判断？是指代？是长难句切分？给出判断方法。
- **易错点解析**：**逐项**说明 A/B/C/D 为什么错或为什么对。错法要归类：无中生有、反向干扰、张冠李戴、程度错误、答非所问、过度推理、偷换范围。

## 6. 全篇装配顺序

`page()` 把上面这些拼成一个完整 HTML，顺序是：

```
页头 header
  ├ 年份 + 篇目
  ├ 主题
  ├ 标签行（题型 / 题号 / 词数 / 难度 / 主题标签）
  └ 目录锚点（第一段 … 第四段 / 真题 5 题 / 变体 6 题 / 核心词汇）

第一段卡片   正文 → 段意 → 语法点
第二段卡片   …
第三段卡片   …
第四段卡片   …

真题区  article × 5
变体区  article × 6
核心词汇区  glossary 表格
全文主旨区  summary

浮动工具栏（七个圆钮）
<script> 朗读与显示开关
```

CSS 与 JS 全部内联在同一个文件里，没有外部请求，所以这个 HTML 可以随便拷、随便发、断网也能看。

## 7. 照做一篇：检查清单

想用这套脚本做一篇新的，按这个顺序：

- [ ] **准备 `SOURCE.md`**：正文按 `## Text N` / `### 第 M 段` 分节，题目按 `### 题目` 分节，答案写 `**答案 X**`。这是唯一权威底本，务必先核对准。
- [ ] **写 `data/textN.words.txt`**：正文逐词，标点也要占 token 写 `|_|_`，段前 `@N`。
- [ ] **跑 `python verify.py 2021 N`**：必须输出「全部一致。」。不一致就按提示的位置改 words.txt——它会告诉你第几段第几个 token 对不上。
- [ ] **写 `data/textN.lesson.json` 的 `para_notes`**：每段一条，段数要与 words.txt 的 `@N` 数量一致。
- [ ] **写 `data/textN.quiz.txt`**：每题 5 块，每块末行 `~` 中文译文。
- [ ] **写 `lesson.json` 的 `questions` 与 `variants`**：真题 5 道、变体 6 道，每题 4 块且 `k` 值顺序固定。
- [ ] **跑 `python qc.py 2021 N`**：必须「全部对应正确。」。它查三件事：块是否齐、块名对不对、quiz 词序列与 lesson 的 stem/options 是否一致。
- [ ] **跑 `python build.py 2021 N`**：看有没有 `!` 告警（音标格式、释义长度、题量）。
- [ ] **跑 `python _final.py 2021`** 和 **`python _allcheck.py 2021`**：核成品结构。
- [ ] **浏览器打开看一眼**：重点看长词那一行有没有挤、段意与语法点卡片是否成形、题目两列是否对齐。

手工从零写一篇大约是这个量级：387 词 ×（1 行 words）+ 55 块 ×（约 8 行 quiz）+ 60 KB 的 lesson.json。所以实践中通常不是一个人手写，而是把「写 words.txt」「写 quiz.txt」「写 lesson.json」拆成三份并行做——这也是这个项目当初真实的做法。
